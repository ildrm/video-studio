# Backups, disaster recovery and restoration

**Status:** proposed. **Owner:** SRE/data lead; security and privacy review. **Dependencies:** storage retention and deployment architecture.

Use [NFR-06](../01-product/non-functional-requirements.md) as the authoritative proposal: metadata RPO ≤15 minutes and RTO ≤4 hours for critical create/open/save operations. These apply to the planned production system independent of subscription; they remain hypotheses until a restore exercise validates them. Media originals and verified exports require versioned durable object storage and an independently protected replication/backup policy; queues and ephemeral proxies can be rebuilt from durable records. Establish an explicit object RPO separately by storage class, region and cost. Backups include database point-in-time recovery, schema version, encryption keys and access policies, project revisions and immutable snapshot references. Retention must honor deletion/legal-hold rules; backup copies have a documented expiry and access process.

Restore into an isolated account: authenticate recovery operators; restore keys and database to chosen timestamp; restore object versions and required configuration; validate referential integrity, sample asset checksums, revision readability, tenant access boundaries, render snapshot dependencies and job reconciliation. Quarantine output until verification succeeds, bring up compatible API/workers, switch traffic with explicit incident approval, monitor and preserve failed environment for investigation. Rebuild queues from durable states, rejecting stale leases and guarding idempotent publication. Record start/end, actual RPO/RTO, checksums, omissions and remediation. Test quarterly initially and after material changes; exercise partial tenant recovery and regional failure. Encryption and separation of backup credentials reduce ransomware blast radius but do not themselves establish compliance.
