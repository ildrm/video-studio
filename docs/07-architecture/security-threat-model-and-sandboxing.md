# Threat model and sandboxing

Status: proposed • Owner: security architect • Dependencies: [tenancy](../04-backend/authentication-authorization-and-tenancy.md), [compiler](../05-media-processing/render-compiler-and-execution-graph.md).

Assets: source media, credentials, project data, tenant isolation, compute and exports. Threats and controls: IDOR → server-side tenant/action checks and negative tests; malicious media → patched, unprivileged, isolated worker with CPU/memory/disk/pid/time ceilings; command injection → typed allowlist and argv arrays, never shell interpolation; SSRF → no user URL input, restricted protocol/egress and server-generated object paths; quota abuse → reservations, per-tenant limits, fair scheduling; stolen signed URL → narrow short TTL, no logs, encryption; compromised worker → job-specific credentials and no host mounts; prompt injection → untrusted content cannot authorize tools or mutate project, explicit approval. Audit privileged and destructive actions; sanitize errors, redact secrets and scan images/dependencies. Process group termination and fencing prevent stale worker publish. Separate customer data from development; incident response and recovery exercises precede launch. Risks are assessed, not claimed mitigated.
